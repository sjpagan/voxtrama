{# The shell's sidebar. A macro, not an {% include %}: its one parameter is explicit, so a page (or a test) can render it without building whatever the rest of the shell needs. `items` is a list of rendering.NavItem: key, href (None when the section has no route yet), active, `children` (Setup's four steps, empty for every other entry today) and `footer`. This template decides nothing about which sections exist, which is current, or what a child's href carries forward (that is rendering.sidebar_items's job), only how each already-decided item looks. There is no "coming soon" branch: rendering.sidebar_items no longer hands this template a section with neither an href nor a child that has one, so every item left to draw is a link. A parent's children render as a nested
    , but only while that parent is active (`item.active`, true when the parent itself or one of its children matches `current`). No JavaScript, no
    : what to show is decided server-side, once, the same way sidebar_items decides everything else. `item.active` alone used to put `aria-current="page"` on both the parent and its active child, two elements claiming the same page. `has_active_child` tells the two states apart. When a child is active, the parent only *contains* the current page and gets a class, not `aria-current`: that attribute is an accessibility statement, and two of them in the same bar would be a false one. The deepest match alone carries `aria-current="page"`. The same condition that reveals the children (`item.children and item.active`) also draws the caret next to the parent's label.
